# SIS implementation decisions

Defaults chosen during implementation, one per line (`- [Area] decision — reason`). Legacy yoklama decisions: `docs/legacy-yoklama/DECISIONS.md`.

- [Core] Packages: `core.person` (Person, PersonService), `core.course` (Course, Enrollment, Chapter, roster, staff), `core.auth` (sessions, CourseAccess, magic link, password login, admin bootstrap), `core.mail` (SMTP/EWS), `core.admin` (people admin). Attendance, exam, classroom, session packages keep their yoklama names — smallest diff to the normative check-in code.
- [Core] Sign-in state is stateless for Spring (SessionCreationPolicy.STATELESS); the `sis_session` cookie is resolved per API request by `SessionAuthenticationFilter` (only `/api/**` and `/actuator/**` hit the DB). Authorities: ROLE_USER, plus ROLE_ADMIN for `system_admin`.
- [Core] Session cookie: HttpOnly, SameSite=Lax, Path=/, 30 days, Secure from `app.auth.cookie-secure` (false in dev/test, true otherwise). Logout deletes the row and clears the cookie; /api/auth/logout is permitAll so an expired session can still clear its cookie (CSRF token still required).
- [Core] CSRF stays as in yoklama (`csrf().spa()`, XSRF-TOKEN cookie → X-XSRF-TOKEN header, /api/public/** exempt); /api/auth/request, /verify and /login also need the token (the SPA calls GET /api/auth/csrf first).
- [Core] POST /api/auth/request answers `{ok:true, onRoster:bool}` — the same information question-pool's `on_roster` gives, nothing more. Max 3 links per person per 15 minutes (as question-pool); rate-limited requests also answer onRoster=true.
- [Core] Magic link eligibility: person with that e-mail, active, not deleted, and (system admin or at least one live enrollment in any role). Archived courses still count.
- [Core] Mail link URL is `{base}/login/verify?token=…`. Base = request's public base URL (X-Forwarded-*); new optional APP_LINK_HOSTS allow-list falls back to APP_PUBLIC_BASE_URL for other hosts (guards against Host-header poisoning of login links). Empty list = trust the request, as instructed.
- [Core] Password login: delegating PasswordEncoder (existing `{bcrypt}` hashes work); any usable person with username + password hash may use it (not only staff). Unknown usernames still run one bcrypt check (timing). Rate limit as before (login-per-ip-per-minute); /request and /verify share a new 10/min/IP bucket.
- [Core] New error code LINK_INVALID (400) for a used/expired/unknown login token.
- [Core] Staff nicknames: `Instructor`, `Instructor2`, … for people created as staff (course staff add, admin bootstrap, admin-created people without a student number); random `CalmOtter42` style for students (roster import/add, admin-created people with a student number).
- [Core] Course creation: system admins and anyone who is staff (OWNER/INSTRUCTOR/ASSISTANT) in at least one course; the creator becomes OWNER. A brand-new instructor therefore needs an admin (or an existing owner adding them as staff) first.
- [Core] Term default when omitted: Sep–Jan → `{year}-FALL` (January belongs to the previous year), Feb–Jun → SPRING, Jul–Aug → SUMMER. Term is upper-cased, `[A-Z0-9-]{1,16}`. Course code is unique per term (schema `uq_course_code_term`).
- [Core] Course settings (code, name, term, language, flags, limits, aiContext) may be changed by any staff member of the course (or admin). Archive/unarchive/delete and staff management: OWNER or system admin.
- [Core] Course delete only without sessions, exams or pool questions (409 otherwise; archive instead). Done with plain SQL so ON DELETE CASCADE removes enrollments and chapters.
- [Core] `attendanceEnabled` / `poolEnabled` are stored and returned; the backend does not block attendance when attendanceEnabled=false (the UI hides it for students). Pool module decides how to enforce poolEnabled.
- [Core] Language values limited to `tr` and `en`; questionsPerChapter 0–100, askAiPerDay 0–1000, aiContext ≤ 20 000 chars. aiContext is null in course DTOs for students.
- [Core] Roster = live STUDENT enrollments of usable (active, not deleted) people. Every roster entry made through SIS has a student number (required in both import formats and in "add one"), because check-in, manual entry and exam results key on it.
- [Core] Roster import: JSON `{text, mode}` (pasted) or multipart `file` + `mode`. Default mode MERGE (yoklama's default was REPLACE); REPLACE soft-deletes STUDENT enrollments that are not in the input. Format detected per line by the `@` (yoklama `no, name[, email]` or question-pool `email, name, no`), separator `;` `,` or tab, header/BOM/quotes as in yoklama.
- [Core] Roster upsert: person by student number, then by e-mail; e-mail/name updated when given; a soft-deleted/inactive person is re-activated (question-pool behaviour); a removed enrollment is re-activated. Conflicts (e-mail owned by another person, e-mail person with another number, person is staff of the course) become per-line errors, not failures of the whole import.
- [Core] Remove from roster / staff = soft delete (`enrollment.deleted_at`); DELETE /roster/{personId} uses the person id (not the student number). A course must keep at least one OWNER; nobody can remove themselves from staff.
- [Core] Adding staff by e-mail re-activates a soft-deleted person and changes the role of an existing enrollment (also STUDENT → staff).
- [Core] Admin people API also has POST (create person with optional username/password) — the old teachers screen could create accounts. PATCH: null = unchanged, "" clears e-mail/studentNo/username/password. Admins cannot deactivate, un-admin or delete themselves. Deactivating or deleting ends all sessions and pending links.
- [Core] Soft-deleted people keep their enrollments rows; every roster/access query filters on the person being usable, so they drop out everywhere and come back unchanged when re-activated.
- [Attendance] Classrooms stay personal (owner = person). Who may create one: staff anywhere or admin. A session may use a classroom owned by the current person, by an admin, or by any staff member of the session's course (so co-teachers can share a room).
- [Attendance] Session list (GET /api/sessions): admins see all; others see sessions of courses where they are staff.
- [Attendance] If a student leaves the roster between attempt start and completion, completion is rejected with NOT_IN_ROSTER (attempt marked REJECTED like other hard rejections).
- [Attendance] Bulk entry: numbers not on the roster are not recorded and come back in a new `notInRoster` list; duplicates still count as `skipped`; invalid formats stay in `errors`.
- [Attendance] my-attendance lists sessions that were ever opened (opened_at not null), oldest first; present = a row exists whose teacher_decision ≠ REJECTED (a pending FLAGGED record counts as present for the student).
- [Exams] Results are roster-only (409 NOT_IN_ROSTER otherwise); the name snapshot always comes from the roster, `fullName` in the request is ignored. `form` (A..) is validated against `exam.forms`; `forms` (1–4) and `seed` accepted on create/update, `poolQuestionId` passed through per question.
- [Exams] my-results returns only exams that have a result for the caller (points = sum of graded answers, max = exam total).
- [Build] H2 removed. Dev profile → jdbc:postgresql://localhost:5433/sis (sis/sis), root compose `db` publishes 127.0.0.1:5433. Tests use one shared Testcontainers `postgres:17-alpine` (`support/PostgresTestcontainer`); the app's compose port 8790 is now bound to 127.0.0.1 too.
- [Build] Angular project renamed `yoklama-web` → `sis-web` (dist path in pom.xml updated). Mail health indicator disabled (an empty SMTP host would turn /actuator/health DOWN).
- [Frontend] Login at `/login` (magic link first, staff password form in a collapsible box; `?staff=1` opens it), `/login/verify?token=` completes it, `/t/login` redirects. returnUrl is honoured only for same-app paths. Staff (staff anywhere or admin) land on `/t`, everybody else on `/courses`.
- [Frontend] Admin people screen at `/t/admin/people` (old `/t/admin/teachers` redirects). Course settings, staff list (add/remove for owner/admin) and roster paste/import live on the staff course page.
- [Pool] Persistence with JdbcClient and map rows (1:1 port of question-pool's SQL); JPA only for `Course` (via CourseAccess) and `ExamResultRepository.countByExam_Id`. Snake_case is kept only in pool/agent JSON: request records carry `@JsonNaming(SnakeCaseStrategy)`, responses are maps keyed by SQL column names.
- [Pool] Errors: new `PoolException` (status + question-pool's English message) rendered by a highest-precedence advice in the SIS error shape `{code, message, details}` (400 VALIDATION_ERROR, 403, 404, 409 CONFLICT, 429 RATE_LIMITED, 502 BAD_GATEWAY). Access failures from CourseAccess keep core's ApiException (Turkish message).
- [Pool] poolEnabled=false: every pool endpoint answers 404 to non-staff and 409 ("The question pool is not enabled for this course.") to staff, so staff see why. Archived courses get no extra restriction.
- [Pool] Non-members of a course get 403 (CourseAccess.requireMember) also on `/api/pool/chapters/{id}` and `/api/pool/questions/{id}`, rather than 404.
- [Pool] "Privileged" (sees unapproved questions, key, AI review; cannot answer; exempt from limits and closed chapters) = author or staff of the question's course (system admins count as staff). Comment author shows "Instructor" when the commenter has (or had) a staff enrollment in that course; `real_name` only for staff viewers.
- [Pool] Ask-AI daily limit counts AI replies to the student's comments within the same course (rolling 24 h), limit from course.askAiPerDay.
- [Pool] AI course description: course.aiContext, or "<code> <name>." when blank. Blank OPENROUTER_URL / OPENROUTER_MODEL fall back to the defaults (deploy compose passes empty strings). X-Title header "SIS Question Pool". AI work runs on the module's own virtual-thread executor.
- [Pool] Participation report = live STUDENT enrollments of people not soft-deleted (inactive people still listed with `active`); all counts restricted to the course. Student detail requires such an enrollment (404 otherwise).
- [Pool] Staff question list accepts `chapter_id` (what the old Vue sent) and `chapterId` (what the old backend read) — fixes question-pool's silently ignored chapter filter.
- [Pool] Additive response fields: `course_id` on GET chapter and GET question; chapter PUT also accepts `number`. Chapter create: number 1–999 unique per course (409), title 1–300; delete only without questions (409), study_state/study_log rows of the chapter cascade.
- [Pool] Exam builder: exam rows with course_id, title (≤120 as before), forms, random seed, created_at from the Clock; exam_question per drawn question: position 1..n in chapter order, CHOICE, choice_count 4, correct_choice, text = left(stem, 2000), topic = left(chapter title, 120), max_points 1, pool_question_id. Swap updates pool_question_id/text/correct_choice; remove renumbers positions. Swap, remove and delete are refused (409) once the exam has results. Builder list = exams of the course with ≥1 pool-linked question; items join through pool_question_id (rows whose pool question was deleted drop out of the builder view).
- [Pool] Exam `counts` keys are chapter ids (as question-pool's web API); MCP create_exam takes chapter numbers. Missing seed (exam made elsewhere) falls back to the exam id for the form shuffle.
- [Agent] MCP token prefix `sis_` (was `qp_`), hint = first 7 + "…" + last 4 characters. Token rows are not deleted when a person is deactivated; lookup requires an active, not deleted person (same effect).
- [Agent] /mcp: permitAll + CSRF-ignored in SecurityConfig; the controller sets the token's person as the SecurityContext principal for the duration of the message (restored afterwards), so CourseAccess and the pool controllers apply unchanged.
- [Agent] Pool courses of a person = pool-enabled, not archived, live enrollment. `course` argument = code (spaces/case ignored) or id; default only when exactly one; ambiguous code across terms needs the id. System admins may address any pool-enabled course by id/code (archived ones last).
- [Agent] Tool audience is checked per course: student tools need a STUDENT enrollment (staff/admins get a clear tool error), teacher tools need staff. tools/list and prompts/list show student items to people with any student pool course and teacher items to people with any staff pool course (or admins). Id-addressed tools (question, flag, comment, exam) take the course from the row. `initialize` instructions: staff text, student text, or both.
- [Agent] import_students delegates to RosterService.importText(mode MERGE), so lines need a student number (core rule) and the result is core's ImportResult (camelCase). Teacher deletion tools did not exist and none were added.
- [Agent] study_log has no course column: entries without a chapter are shown to the student in get_progress of every course but not to staff in student_detail; staff see only entries about chapters of their course. No V1 change.
- [Agent] Prompts and tool texts say "chapter" instead of "week"; prompt argument names (`week`, `count`) kept, plus optional `course`.
- [Integration] Migration: the bootstrap admin's nickname is regenerated when its row is taken over — the app names it `Instructor`, which question-pool already uses; found when rehearsing on an app-created database.
- [Integration] Production sets `APP_LINK_HOSTS` to the SIS hostname plus the two old hostnames, so mailed login links cannot be pointed elsewhere by a forged Host header.
- [Integration] Uncommitted MCP work in the question-pool folder was ported from its working tree; that folder was not modified or committed.
- [Topics] Topics are derived only from `## N. Title` level-2 headings (N = digits, `N.` then optional title); headings inside fenced code blocks are ignored; when one document repeats a number, the first heading wins for title and section content; titles are trimmed; section content drops trailing blank lines.
- [Topics] TopicSync runs on start-up only for chapters without topics (an ApplicationRunner; a failure is logged, not fatal), after every staff chapter POST and after a chapter PUT that sends `doc_en` or `doc_tr`, and on demand; a stale topic that is still linked keeps its old titles.
- [Topics] `GET /api/pool/courses/{id}/topics` needs only membership (no `poolEnabled`), like the topic preview, because exam editors and exam results use topics in courses without the pool. Sync and link changes are pool staff actions (pool switch applies).
- [Topics] `topic_ids` on question create/update: absent/null = unchanged (none on create), list = replace, duplicates ignored, unknown or foreign ids → 400 "A topic does not belong to this course.". The staff `PUT …/questions/{id}/topics` answers `{ok, topics}` and works in every state; authors may set topics on their own questions (create and while editable).
- [Topics] `topics` is added to every question row the pool returns (GET/attempt, mine, chapter list, staff list), not only to single-question responses; the pool exam builder item list is unchanged.
- [Exams] Exam question `topicIds` null = keep explicit links on update (none on create); foreign topic → 400 `details["questions[i].topicIds"]`. Effective topics = explicit ∪ the pool question's topics, ordered by chapter number, topic number.
- [Exams] `published` is added to the exam list rows too. Result detail: missed = graded and points < maxPoints (ungraded or missing answer rows are not missed); `reviewTopics.total` counts all of the exam's questions with the topic; `correct` only for CHOICE with a key and an answer row; `myAnswer` null for FREE.
- [Exams] Question text cap raised from 2000 to 20 000 characters (column `text`); explanation cap 20 000, option text/rationale 5 000. `explanation` null = unchanged on update, blank clears; `options` null = unchanged, list replaces; OPEN/FREE accept only `[]`. Stored options are not trimmed when choiceCount shrinks or the type changes without `options`.
- [Exams] Result-detail statistics are computed in ExamService from the loaded snapshot rather than ExamAnalysisService: the analysis is staff-only, keyed by student, and its success rate is earned/max, while the student view needs the full-points share. `stats.maxPoints` (top level) = highest total in the class, since the possible maximum is already the top-level `maxPoints`.
- [Agent] `read_topic` and `list_topics` are ALL-audience tools (staff can read topics too); `read_topic` falls back to the other language with a `note` when the requested one has no section. `review_topics` ranks by exam missed + pool wrong first answers, then exam missed, chapter, number; `get_progress.weak_topics` = its top 5. `topic_stats` counts exam answers of all exams of the course (published or not); exam correct share = graded answers with full points.
- [Agent] MCP exam tools return the core camelCase DTOs (`my_exam_results`, `publish_exam`) unchanged, so the web page and the agent see the same data.
- [Topics] Midterm 1 is migrated unpublished; students see the exam review page only after staff publish the exam.
- [Topics] Migration order: migrate.sql → verify.sql → private/link-midterm1.sql (text, Form A options with rationales, explanation, pool link) → start the app once (topics are derived from headings) → link-topics.sql (97 questions, 109 links).
- [Repo] Public repository: the Midterm 1 answer key script lives in git-ignored `migration/private/`, the owner's question-pool e-mail is a psql variable (`owner_qp_email`) — exam keys and staff e-mails must not be published.
- [Students] Staff student page `/t/courses/:id/students/:personId` (roster number and name link to it) combines one new endpoint `GET /api/courses/{id}/students/{personId}` (requireStaff; profile + one row per opened session, state PRESENT/PENDING/REJECTED/ABSENT with source, flags, teacher note) with the existing exam-learning (by student number) and pool student-detail (only when `poolEnabled`) endpoints, so each module keeps its own rules. Needs a live STUDENT enrollment of a not-deleted person (inactive people still open), 404 otherwise.
- [Students] On that page attendance rate = PRESENT / opened sessions; flagged records without a decision are shown as pending and do not count yet (the student's own page counts them, since only REJECTED is absence there). Exam success = earned / possible over exams with a result.
- [Exams] Answer entry keeps unsaved sheets in localStorage (`sis.examEntryDraft.<examId>`, keyed by student number) so a reload, closed tab or navigation does not lose them; a draft is restored when the student is opened again (with a note and "Taslağı at"), dropped on save, on a confirmed discard or when it equals the server result, ignored when the exam's questions changed, and all drafts are cleared on logout (shared computers). A draft started from an older server result is still restored, with a warning.
- [Exams] Answer-entry drafts are also kept on the server (`exam_entry_draft`, V3; `GET/PUT/DELETE /api/exams/{id}/drafts[/{studentNo}]`, course staff only). The sheet is the client's draft JSON stored as `jsonb` (object, ≤ 500 000 chars, student-number format checked, no roster check since drafts are not results); last writer wins; saving or deleting the result removes the draft in the same transaction. The client sends a draft 1.5 s after typing pauses (one request at a time, retried after 15 s on network/5xx errors) and merges browser and server copies without client clocks: unsynced local edits win, a synced local copy follows the server (taken over when changed, dropped when gone), server drafts of another question layout are deleted. Logout clears only the browser copy.
- [Exams] Choice options are a label set, not a count: `exam_question.choice_labels` holds one character per option ("ABCD", "DY", "TF", "10"), 2–10 distinct characters from A–Z/0–9 (single characters keep the one-key answer entry). `choiceCount` stays in the DTO as the length and is still accepted in requests (A.. of that many); rows without labels (pre-V4, pool builder) fall back to A.. of `choice_count`. Answers, keys and option letters must be one of the labels; a change of the label set rescores the question like a key change. Option order is label order, so the shuffle of printed pool forms (A–D) is unaffected.
- [Exams] Sub-questions are a presentation grouping, not a question type: `exam_question_group` (exam, position, text, html) and `exam_question.group_id` / `sub_label`. Scoring, answers, topics and analysis stay per `exam_question`; a group has no points of its own. Questions of a group must be consecutive in entry order (400 otherwise); groups without questions are dropped on save. Printed numbering is shared: Q1, Q2, group(Q3, Q4), Q5 print as 1, 2, 3a, 3b, 4 (`label` on QuestionDto/MyQuestionDto/QuestionAnalysisDto/MissedQuestionDto, group `position` = its number; CSV columns `S3a`). `position` keeps the entry order the answer-entry keyboard and export keys rely on. A blank `subLabel` prints a, b, … by order.
- [Exams] Rich content: `html` on questions and groups (≤ 500 000 chars, room for pasted inline images). It is staff-written and shown to students, so it is sanitized with DOMPurify both when it leaves the editor and on every render (`app-rich-html`), never trusted raw; the server stores it as given. When present it replaces the plain `text` on screen; `text` stays for one-line summaries and the pool builder.
- [Exams] Printable per-student report (`/t/exams/:id/sheets[?student=]`, "Öğrenci dökümleri"): built client-side from the exam definition and the results already served (no new endpoint), one page per student with group stems, question content, options, the given answer, the key, right/wrong/blank and points; the student's own review page got the same content and a print button. The report includes the answer key, so it is staff-only until the exam is published.
- [Tests] Testcontainers on eas: the Docker daemon runs with user namespaces, so the privileged Ryuk helper cannot start; run the backend tests with `TESTCONTAINERS_RYUK_DISABLED=true` there (containers are still stopped by the JVM's shutdown hook).
- [Exams] A label-set change that keeps the number of options (AB → TF, AB → 10) renames by position: stored answers, option letters and (in the editor) the key move with their index, and the question is rescored, so switching an entered exam from A/B to T/F changes no score. A change of size keeps letters as they are (out-of-range ones score 0, as before).
- [Exams] Publishing still sends nothing by itself. A separate staff action `POST /api/exams/{id}/notify` (published exams only, 409 otherwise) mails every student with a result and a roster e-mail: an optional note (≤ 4 000 chars), the score, a link to the review page and, on request, the per-student report in the body (plain text + HTML alternative; rich content reduced to text, images left out, the link leads to the full page). `exam.notified_at` / `notified_count` (V5) show the last send on the exam page. Addresses come from the roster, never from the result snapshot.
